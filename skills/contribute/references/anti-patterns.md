# Named anti-patterns

> Empirical catalog of how outside contributions fail at high-velocity OSS
> repos. Each pattern is named, defined, sourced to a real PR, and tied
> to a gate (or to a future gate listed in `~/.contribute-system/ROADMAP.md`).
>
> Maintained by: whoever audits a failing PR — append, never rewrite. New
> patterns get added when seen at least twice across distinct repos.
>
> Referenced from: `SKILL.md` § "Trust-ladder discipline".

## How to use this catalog

1. Before drafting any contribution at a repo, read the patterns and ask
   "would mine match one of these?"
2. When a `/contribute` gate fires BLOCK, the fix_hint often names the
   matched pattern (e.g., `A07` → "Trust-Ladder Skip"). Look it up here for
   the *why*.
3. When auditing a closed-without-merge PR, score it against the
   signatures at the bottom of this file. If it matches 3+, append a case
   study under the matching pattern.

## Pattern 1 — The Audit Dump

**Definition**: a single PR that adds a large directory of generated
audit/scan/review/finding artifacts to the upstream repo's tree, declares
"no source changes," and asks the maintainer to absorb the workspace and
decide what to do with it.

**Why it kills the PR**: the artifacts are the *contributor's* work product,
not the *project's*. Dumping them into the upstream's `.audit/` or
`.review/` or `.exorcism/` directory commits the maintainer to hosting
scaffolding they didn't ask for. The diff is unreviewable because there's
no central code change — nothing to verify against tests, nothing to assess
against project goals. The maintainer's only real options are
(a) read the contributor's executive guide and trust 100+ separate findings
or (b) close the PR. Most pick (b), even when the underlying audit is good.

**Real cases**:

- **`oven-sh/bun#30903`** ([link](https://github.com/oven-sh/bun/pull/30903)) — 983 files, +122,702 / -0, 11 commits. Generated by Claude + Codex + Gemini. Asked maintainers to "decide whether to accept this PR as-is or move the artifacts to an external location." After 11 days: 1 drive-by comment fixing a broken link in the PR description, 3 thumbs-down, 0 maintainer reviews. This is the canonical case; the whole trust-ladder rule is named after it.
- **`oven-sh/bun#30763`** ([link](https://github.com/oven-sh/bun/pull/30763)) — 121 files, +52,061 / -0, 44 commits. *Same author, two days earlier than #30903.* Body literally says "This is an audit drop only — zero source changes in this PR." Reviews exclusively from `claude[bot]` and `coderabbitai[bot]`; the author then replies to his own bots. 13+ days open, no maintainer comment. Establishes that the maintainer non-response to #30903 was a consistent rejection of the shape, not a one-off bandwidth issue.

**Gates that catch it**:
- `B13-trust-ladder-size` — refuses the size at rung 0/1-3 before commit
- *(future)* `A1-no-audit-dump` — pattern-matches `.audit/`, `.review/`,
  `*-exorcist/`, etc. as new top-level dirs with >50% additions in one
  directory tree. Tracked in `ROADMAP.md`.

**Right shape instead**: host the audit artifacts in *your* repo, link them
from a Design Issue summarizing the top N findings, then file individual
fix PRs that close one finding each. Dicklesworthstone (the bun#30903
author) actually did this — see his #31087, #31092, #31093, etc. — but
filed them alongside the unread audit-PR, which is its own anti-pattern
(see Pattern 4).

## Pattern 2 — The Trust-Ladder Skip

**Definition**: a contributor's first PR to a repo is a multi-area
proposal, umbrella refactor, or "everything we should change" pitch that
requires the maintainer to trust the contributor across many decisions
before they've earned trust across one.

**Why it kills the PR**: maintainer review attention is the single
scarcest resource on a high-velocity project. Reviewing an umbrella from
an unknown contributor costs more than reviewing a small fix from a known
one; the rational response is to wait until the contributor has shipped
a small fix first. So the umbrella sits.

**Real cases**:
- **`oven-sh/bun#30903`** — same case, viewed through the trust-ladder
  lens. Dicklesworthstone had 0 prior merged PRs in `oven-sh/bun`. His
  *first contact* was a 122k-line proposal. Maintainer ratio: dozens of PRs
  merged in the same 11-day window, just not this one.
- **`nodejs/node#61935`** ([link](https://github.com/nodejs/node/pull/61935)) — "Audit of Node.js Technical Improvements and Bug Fixes," opened 2026-02-22 08:01 UTC by poria-lang (0 prior merges in Node.js). Diff was small (9 files, +106/-113), but the *framing* was umbrella ("audit covering webstreams, cluster tests, http2 docs, fs.promises perf"). **Closed 15 minutes later** by @ChALkeR (Node.js TSC) with the one-line review: "Just random hallucinated changes." Demonstrates that the trust-ladder failure is about *framing*, not just file volume.

**Gates that catch it**: `A07-trust-ladder-fit` + `B13-trust-ladder-size`.

**Right shape instead**: find one open issue, fix it in ≤200 LOC, ship it.
Get merged. Repeat 3-4 times. Then pitch your umbrella with the social
proof of recent merges.

## Pattern 3 — The Maintainer-Decision Punt

**Definition**: the PR's body or test plan asks the maintainer to make a
scope decision the contributor should have made before filing. Phrases
like "decide whether to (a) accept this as-is or (b) move the artifacts
to an external location," "let me know if you want me to split this," or
"happy to do whatever you prefer" appear in the PR body.

**Why it kills the PR**: it converts the maintainer's review-time into
*your* product-management time. A maintainer who has 50 other PRs to look
at this week is not going to invent your scope strategy for you. They'll
either close it or never click into it.

**Real cases**:
- **`oven-sh/bun#30903`** — test plan literally includes: "Decide whether to (a) accept this PR as-is (audit artifacts in-tree, fixes follow in separate PRs) or (b) move the artifacts to an external location (e.g., a separate audit repo) and reduce this PR to the executive guide + the META scripts." That's not a test plan, that's a question for the maintainer.

**Gates that catch it**:
- *(future)* `C2-no-maintainer-decision-punts` — phrase-detector pass over the PR body. Tracked in `ROADMAP.md`.

**Right shape instead**: decide first, file second. If the decision is
genuinely the maintainer's call (e.g., "should this feature live in core
or as a plugin?"), file as a Design Issue, *not* a PR.

## Pattern 4 — The Review Queue Pile

**Definition**: contributor opens 2+ unreviewed PRs on the same repo in
quick succession, often building one on top of the other or claiming
they're "independent" when they share context the maintainer hasn't yet
seen.

**Why it kills the PR**: each new PR raises the cost of looking at any of
them. The maintainer can't review #2 without context that's still
unmerged in #1. The pile produces a review deadlock — the maintainer
postpones reviewing any of them until the umbrella context (or the first
PR) is dealt with.

**Real cases**:
- **`oven-sh/bun` Dicklesworthstone batch (#31087, #31092, #31093, #31107, #31108, #31140, #31204, #31248, #31258, #31267)** — 10 surgical fix PRs filed across 4 days (May 19-23, 2026) while the umbrella audit-PR #30903 sat unread. Each individual PR is genuinely well-shaped: closes a specific `EXP-NNN` finding, has a Miri witness, includes an in-repo test. But the maintainer can't review any of them without the audit context that's stuck behind their #30903 vote. All 10 still open as of 2026-05-28.

**Gates that catch it**:
- *(future)* `D6-review-queue-throttle` — refuses to open a 3rd PR when 2 prior PRs on the same repo are unreviewed. Tracked in `ROADMAP.md`.

**Right shape instead**: ship one. Wait. If reviewed: ship the next. If
silent after >7 days: comment politely on the silent PR offering to split
or pause; *do not* open another PR.

## Pattern 5 — The Generated-Artifact Bloat

**Definition**: the diff is dominated by generated material with no
human-engineered code at its center: per-finding JSON registries, raw
ast-grep output, every round's convergence file, vendored Cargo build
trees, transpiler output, etc.

**Why it kills the PR**: a maintainer cannot review what they cannot
read. A 50KB JSON registry of findings doesn't compile, doesn't pass
tests, doesn't fit in the project's mental model. Generated content
belongs in your repo or a gist; only the *summary* belongs in the
maintainer's tree.

**Real cases**:
- **`oven-sh/bun#30903`** — includes `phase1_*` through `phase11_*` JSON files, every round's convergence JSON, per-EXP Miri/loom logs, raw ast-grep output, per-experiment Cargo build trees (excluded via `.gitignore` only because the author explicitly noted them).
- **`oven-sh/bun#30763`** — 44 commits, most of which are the author tidying his own audit dir ("drop empty scratch files," "restore .log files," "re-drop raw dumps").

**Gates that catch it**:
- `B13-trust-ladder-size` catches it on size + new-top-level-dir grounds.
- *(future)* `A1-no-audit-dump` would name it explicitly.

**Right shape instead**: include the executive summary in the PR (or as
a Design Issue). Link out to the artifact corpus hosted in your repo.

## Pattern 6 — The Multi-Agent Authorship Brag

**Definition**: the PR body or commit footers prominently advertise that
multiple AI agents contributed (Claude + Codex + Gemini + ChatGPT + ...).
The framing positions multi-agent generation as a credential.

**Why it kills the PR**: for a maintainer who has already been targeted
by AI slop, "Claude, Codex, and Gemini all contributed" is a red flag, not a
credential. The maintainer reads it as "this contributor has limited
ability to validate the output of any one agent and is hoping that
ensemble agreement substitutes for first-principles understanding."

**Real cases**:
- **`oven-sh/bun#30903`** — body says "Multi-agent authorship. Claude, Codex, and Gemini all contributed. Per-doc attribution is in the `CODEX_*.md` filenames." Reactions: 3 thumbs-down.
- **`oven-sh/bun#30763`** — Co-Authored-By footer cites `Claude Opus 4.7 (1M context)`. Reviews dominated by `claude[bot]` and `coderabbitai[bot]`; no human maintainer engages.

**Gates that catch it**:
- *(future)* — there isn't a clean gate for this. The dossier's
  `ai_disclosure_required` field captures the repo's *policy*; the
  contributor needs judgment about whether to *additionally* advertise
  multi-agent authorship in the PR body. Currently advisory only.

**Right shape instead**: disclose AI assistance honestly (commit footer
is fine, per-repo policy applies), but don't position the multi-agent
fact as a strength. A maintainer cares about your validation rigor, not
your tool stack.

## Pattern 7 — Frontmatter Bluff

**Definition**: declaring tools, permissions, or capabilities in skill /
plugin / agent frontmatter that the body never actually uses. The
contributor pads `allowed-tools` (or `tools:`, or `permissions:`) "just
in case," and the body uses a strict subset.

**Why it kills the PR**: maintainers reviewing a skill cross-check the
frontmatter against the body. An over-declared `allowed-tools` reads as
either careless (didn't audit) or sloppy (didn't trim before sending).
Worst case it grants the runtime permissions the skill doesn't need,
which is a security smell. Maintainer asks why X is in there; contributor
has to drop them and push again.

**Real cases**:

- **`kobiton/automate#64`** ([comment](https://github.com/kobiton/automate/pull/64#discussion_r3324558664)) — `run-automation-suite/SKILL.md` declared `Write` in `allowed-tools`. The body uses `Edit` exclusively and never invokes `Write`. Tu Nguyen (Kobiton): "`Write` in `allowed-tools` isn't backed by the skill body: the body uses `Edit` explicitly and never calls `Write`. Suggest dropping it." Fix: drop the tool from the frontmatter list.

**Gates that catch it**:
- `C21-skill-frontmatter-vs-body` — for each modified `**/SKILL.md`, parses the `allowed-tools:` block and asserts every top-level tool name (Read/Write/Edit/Glob/Grep/etc.) appears verbatim somewhere in the body.

**Right shape instead**: trim `allowed-tools` to the minimum set the
body actually uses. If you anticipate a future need, leave it out and
add it when the body grows to need it — not before. Bash sub-permissions
(`Bash(npm:*)`, `Bash(sleep:*)`) are harder to verify by grep and live
under a separate looser policy, but the top-level tool list is exact.

## Pattern 8 — CLI-Centric Skill in a Multi-CLI Plugin

**Definition**: a skill (or skill section) uses Claude-only vocabulary
— `claude mcp`, "Claude Code session", `/mcp` framed as Claude-exclusive
— inside a plugin whose README, AGENTS.md, or `.codex/` /
`gemini-extension.json` / `.cursor/mcp.json` declare cross-CLI support
(Cursor, Codex CLI, Gemini CLI, GitHub Copilot CLI, Continue, Cline).

**Why it kills the PR**: the plugin's marketing surface promises "works
with N CLIs"; the skill docs promise "works with Claude." A user on
Codex/Gemini/Copilot reads the auth section, hits a `claude mcp add`
instruction, and bounces. The maintainer flags the discrepancy on review.

**Real cases**:

- **`kobiton/automate#64`** ([comment](https://github.com/kobiton/automate/pull/64#discussion_r3324565812)) — `run-automation-suite/SKILL.md` Authentication section used `Claude Code session` in the auth-table row and `claude mcp` in the closing paragraph, in a plugin whose README declares support for Claude Code, GitHub Copilot CLI, Gemini CLI, and Codex CLI. Tu Nguyen (Kobiton): "The Authentication section assumes Claude-only. Both the table row description and the `claude mcp` paragraph need to generalize across the five supported CLIs." Fix: rewrite as "AI-CLI session" + cite per-CLI MCP-auth commands (`/mcp`, `/mcp auth <server>`, browser flow) with a pointer to the README.

**Gates that catch it**:
- `C22-cross-cli-vocabulary` — when the target repo declares multi-CLI support (signal: `AGENTS.md` present, `.codex/` present, `.cursor/mcp.json` present, `gemini-extension.json` present, or README references ≥2 of Cursor/Codex/Gemini/Copilot/Continue/Cline), greps modified skill files for `claude mcp` / `Claude Code session` and warns.

**Right shape instead**: name the host-neutral concept ("AI-CLI",
"agent"), and if you need to mention a specific invocation, give the
per-CLI matrix in one breath (e.g. "`/mcp` in Claude Code, `/mcp auth
<server>` in Copilot CLI + Gemini CLI, browser flow on first tool call
in Codex CLI") with a pointer to the plugin README's install section as
the source of truth for current commands.

## Pattern 9 — MCP Annotation Conflation

**Definition**: setting MCP tool-hint annotations in ways that violate
the [MCP 2025-06-18 spec](https://modelcontextprotocol.io/specification/2025-06-18/server/tools).
Two specific shapes:

(a) **idempotentHint on readOnlyHint:true tools** — the spec says
`idempotentHint` is *ignored* when `readOnlyHint: true`. Declaring it
adds clutter and signals the contributor didn't read the spec.

(b) **destructiveHint:true + idempotentHint:false because "destructive"**
— destructive and idempotent are orthogonal. HTTP DELETE is destructive
AND idempotent: a second DELETE against the same resource is a no-op,
not a duplicate side-effect. `terminateSession`, `terminateReservation`,
`cancelOrder` etc. follow the same pattern. Conflating the two
mis-advertises tool semantics to clients (Cursor, ChatGPT Apps SDK,
Continue/Cline) that rely on these hints for retry/dedup logic.

**Why it kills the PR**: maintainers who know the spec catch both
shapes immediately. The fix is mechanical (drop / flip) but it's a full
round-trip — push, re-review, re-push.

**Real cases**:

- **`kobiton/automate#74`** ([review](https://github.com/kobiton/automate/pull/74#pullrequestreview-3422055000)) — initial PR set `idempotentHint: true` on 7 read-only tools (listApps, getApp, listDevices, getDeviceStatus, listSessions, getSession, getSessionArtifacts) and `idempotentHint: false` on 2 destructive idempotent tools (terminateReservation, terminateSession). Tu Nguyen (Kobiton) requested both shapes fixed: "`idempotentHint` is meaningless when `readOnlyHint: true`. Keep `openWorldHint: false` on all 12." and "`terminateReservation` and `terminateSession` are destructive but idempotent — flip `idempotentHint: false → true`." Fix landed in [`4d1c00b`](https://github.com/jeremylongshore/automate/commit/4d1c00b): 17 added lines (vs the original 24), surface now matches spec.

**Gates that catch it**:
- `C23-mcp-tool-annotations-spec` — for any modified `tools/**/*.yaml`
  declaring an `annotations:` block, walks each tool stanza and warns when
  (a) `idempotentHint` is set alongside `readOnlyHint: true`, or
  (b) `destructiveHint: true` co-occurs with `idempotentHint: false`
      (the destructive-AND-idempotent pattern).

**Right shape instead**: read the spec section *Tool annotations* once
before declaring any. The four hints — `readOnlyHint`, `destructiveHint`,
`idempotentHint`, `openWorldHint` — are independent dimensions. For
read-only tools, set `readOnlyHint: true` + `destructiveHint: false` +
`openWorldHint` per the repo's bounded-vs-unbounded character; skip
`idempotentHint`. For destructive tools, decide idempotency on its own
merit — does a repeated call produce additional state change, or is it a
no-op against the already-terminated resource? If no-op, `idempotentHint:
true`.

## Pattern 10 — Engagement-Frame Leakage

**Definition.** Shipping engagement-internal taxonomy (finding numbers,
review-phase labels, op-rule citations, pilot provenance, author
footers, cross-refs to private workspace paths) as if it were common
knowledge in a customer-facing public artifact (plugin source, agent
bodies, skill references, hook scripts, README sections, PR bodies of
public-repo PRs).

**Why it kills the PR.** Maintainers read engagement-frame language as
"this contributor is delivering to their employer, not to my users."
The substance of the change may be genuine customer value, but the
framing signals divided loyalty — they're now reading every paragraph
through "who is this actually for?" The mental model has shifted from
*contributor → community* to *contractor → invoiced client*, and the PR
description has to do the work of dragging it back. Most won't bother.

**Canonical example.** `kobiton/automate#70` (2026-06-03 review by
`huytunguyenn`): the PR shipped a `validate-userintent` PreToolUse hook
that enforced a strict `[partner=<name>] <verb> | contact:<email>`
format on the `userIntent` argument. That format came from the
engagement's own op-rule #4 — internal audit-trail discipline for
Jeremy's Claude sessions, not a customer-facing requirement.
Maintainer's CHANGES_REQUESTED was unambiguous: drop the hook, format
discipline belongs in the contributor's tooling, not the shipped plugin.
The same review-pass also surfaced four sister PRs (`#65`, `#67`, `#75`,
`#77`) carrying F-series finding numbers, "R2 audit pilot" framing, and
author footers in committed file content.

**Real cases.**

| PR | Leak |
|---|---|
| `kobiton/automate#70` | `validate-userintent` hook enforcing engagement-internal userIntent format on every plugin user |
| `kobiton/automate#65` | "Two batches: the R2 audit (Intent Solutions pilot) and the post-R3 external audit" in customer-facing Known Limitations preamble |
| `kobiton/automate#67` | "Per R2 audit finding F25 + F26" / "per R2 F22" in agent body text as if F-IDs were common knowledge |
| `kobiton/automate#75` | "Relationship to engagement deliverables" + `000-docs/043-AAR-CONSO-…` reference in PR body |
| `kobiton/automate#77` | Whole-PR consolidated audit catalog in `/docs` duplicating closed issues |

**Right shape instead.** Two questions before pushing a contribution to
a public repo:

1. Will a customer who clones this fresh from main encounter this
   token? If yes, would they understand it without reading my private
   workspace?
2. If a maintainer searched this token across the repo three months
   from now, would the result mean anything to them?

If either answer is no, the token is engagement-internal and either
moves to the contributor's own tooling (which the gate enforces) or
gets rephrased as a behavior description anchored on the public closed
issue that documents it. The substance — the agent workaround, the
documented limitation, the advisory hook — stays in the contribution;
only the framing changes.

**Gates that catch it.** `c24-engagement-frame-leakage` scans added
lines in the staged diff for finding-ID tokens (`\bF\d+\b` near
`finding|audit|issue|catalog`), review-phase labels (`R[123]
audit|review|deliverable|§`), `Intent Solutions pilot`, `op-rule #\d+`,
`partner=intentsolutions`, cross-refs to `000-docs/NNN-XX-XX-...`
paths, and author footers in committed file content. Severity: WARN
(maintainers may legitimately want some of these for narrow audit
deliverables); a single hit asks the contributor whether the token is
truly common knowledge in the target repo.

## Pattern 11 — Maintainer-URL Leakage

**Definition.** Shipping maintainer-internal issue or PR URLs
(`https://github.com/owner/repo/issues/N`, `owner/repo#N`) in
customer-facing prose — agent bodies, SKILL.md workflow steps, README
user sections, plugin output templates. Same family as **Pattern 10
(Engagement-Frame Leakage)** but a distinct failure mode: the URLs are
the *maintainer's own* tracker, not the contributor's engagement
artifacts, and they show up because the spec author found it useful
for human contributors to chase the evidence — not because the
customer needs the link.

**Why it kills the credibility of a customer-facing surface.** A
paying customer reading a SKILL.md or an agent diagnosis report sees
`per [#36]` and reads "this product is unfinished — the maintainers
are still cross-referencing their own tickets in the docs." It signals
documentation churn even when the underlying product is mature. For an
LLM consuming the agent body as a system prompt, the URL is dead
weight: the model cannot follow it, and the *behavior* is already
encoded in the prose next to it ("post-`terminateSession` ~5 min
cooldown" — the URL adds nothing the model can act on).

**Canonical example.** `kobiton/automate#67` (2026-06-04): the
`device-picker` agent and `run-automation-suite/SKILL.md` § 2 carried
three maintainer issue URLs (#33 four-conflict-modes, #36 cooldown,
#55 token-cap pagination). Each was added during a review-cycle to
"anchor the behavior in evidence" — defensible while the work was in
review, not defensible once shipping to paying customers. Stripped in
the same review pass with the rule: the behavioral language (`"choose
conservatively"`, `"treat truncation as incomplete"`, `"~5 min
cooldown"`) is what steers behavior; the URL is audit trail.

**Where issue/PR URLs DO belong.** Catalog and reference files whose
explicit job is "look up the source":

| Location | Why URLs belong here |
|---|---|
| `references/known-limitations.md` (or equivalent) | The file IS a catalog of platform behaviors with one-per-finding evidence link. Stripping URLs defeats the file's purpose. |
| `CHANGELOG.md` | Per-release evidence anchor — humans reading release notes want the link. |
| `docs/decisions/`, `docs/adr/` | Architecture-decision records explicitly track the issue/PR that triggered each decision. |
| `.github/ISSUE_TEMPLATE/`, `.github/pull_request_template.md` | Contributor-facing surfaces by definition. |
| Commit messages | Tracking-only metadata — not part of the shipping surface. |

**Where they DO NOT belong.**

| Location | Replacement |
|---|---|
| `agents/*.md` body prose | Inline the behavioral description; let `references/*.md` carry the URL. |
| `SKILL.md` workflow steps | Same — describe the behavior, route the user to a `references/` file if they need source-evidence. |
| `README.md` user-guide sections | Plain prose. README's contributor section is different — issue links there are OK. |
| Plugin tool/skill output templates | Whatever the agent emits to a user must read as customer guidance, not maintainer notes. |

**Right shape instead.** Before shipping a contribution, grep the diff:

```bash
git diff origin/main..HEAD \
  | grep -E '^\+' \
  | grep -E 'github\.com/[^/]+/[^/]+/(issues|pull)/|\b[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+#[0-9]+\b'
```

For each hit: is the file a catalog/reference file (URL belongs) or a
customer-facing surface (URL goes; behavioral prose stays)?

**Gates that catch it.** `c25-maintainer-url-leakage` scans the diff
for issue/PR URLs in customer-facing files (`agents/*.md`, `SKILL.md`,
`README*`) and skips the legitimately allowed paths
(`references/`, `CHANGELOG`, `docs/decisions/`, `docs/adr/`, anything
under `.github/`). Severity: WARN.

## Common signatures (for grading a closed PR or pre-flighting yours)

If 3 or more of these appear, the PR almost certainly hit one of the
patterns above. Use as a checklist before clicking "Create pull request":

1. ☐ PR body announces "audit" / "comprehensive" / "exhaustive" /
       "every X" / "all Y"
2. ☐ File count vastly exceeds the lines-changed-per-file ratio
       (generated material, not engineered code)
3. ☐ AI co-author lines on every commit (Claude / Jules / Codex / etc.)
4. ☐ Author has 0 prior merges in the target repo
5. ☐ Bot reviews (CodeRabbit, Claude, Gemini) dominate the review pane;
       human maintainers are absent or one-line dismissive
6. ☐ PR body includes "decide" / "let me know" / "your call" /
       "agent operating route" / "happy to do whatever you prefer"
7. ☐ Self-replies and self-cleanup commits dominate the timeline (the
       author tidying their own work in the review thread)
8. ☐ "Test plan" includes "maintainer reads X document"

## When to add a new pattern

A new entry lands when:
- You've personally observed the same failure mode at **two or more
  distinct repos** (not just one bad PR — that's a case study, not a
  pattern); OR
- The pattern has a clean, gate-able definition that fits the existing
  `gates/<phase><N>-<slug>.sh` slot system; OR
- A maintainer of any tracked repo (per `~/.contribute-system/research/*`)
  has called out the pattern by name in a review comment or
  CONTRIBUTING.md.

When adding a new pattern, also propose the gate that would catch it
(even if you don't ship the gate immediately) and append it to
`~/.contribute-system/ROADMAP.md`.
