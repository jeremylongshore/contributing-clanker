# Named anti-patterns

> Empirical catalog of how outside contributions fail at high-velocity OSS
> repos. Each pattern is named, defined, sourced to a real PR, and tied
> to a gate (or to a future gate listed in `~/.contribute-system/ROADMAP.md`).
>
> Maintained by: whoever audits a failing PR — append, never rewrite. New
> patterns get added when seen at least twice across distinct repos.
>
> Referenced from: `SKILL.md` § "Trust-ladder discipline".

## How to use this catalog

1. Before drafting any contribution at a repo, read the patterns and ask
   "would mine match one of these?"
2. When a `/contribute` gate fires BLOCK, the fix_hint often names the
   matched pattern (e.g., `A07` → "Trust-Ladder Skip"). Look it up here for
   the *why*.
3. When auditing a closed-without-merge PR, score it against the
   signatures at the bottom of this file. If it matches 3+, append a case
   study under the matching pattern.

## Pattern 1 — The Audit Dump

**Definition**: a single PR that adds a large directory of generated
audit/scan/review/finding artifacts to the upstream repo's tree, declares
"no source changes," and asks the maintainer to absorb the workspace and
decide what to do with it.

**Why it kills the PR**: the artifacts are the *contributor's* work product,
not the *project's*. Dumping them into the upstream's `.audit/` or
`.review/` or `.exorcism/` directory commits the maintainer to hosting
scaffolding they didn't ask for. The diff is unreviewable because there's
no central code change — nothing to verify against tests, nothing to assess
against project goals. The maintainer's only real options are
(a) read the contributor's executive guide and trust 100+ separate findings
or (b) close the PR. Most pick (b), even when the underlying audit is good.

**Real cases**:

- **`oven-sh/bun#30903`** ([link](https://github.com/oven-sh/bun/pull/30903)) — 983 files, +122,702 / -0, 11 commits. Generated by Claude + Codex + Gemini. Asked maintainers to "decide whether to accept this PR as-is or move the artifacts to an external location." After 11 days: 1 drive-by comment fixing a broken link in the PR description, 3 thumbs-down, 0 maintainer reviews. This is the canonical case; the whole trust-ladder rule is named after it.
- **`oven-sh/bun#30763`** ([link](https://github.com/oven-sh/bun/pull/30763)) — 121 files, +52,061 / -0, 44 commits. *Same author, two days earlier than #30903.* Body literally says "This is an audit drop only — zero source changes in this PR." Reviews exclusively from `claude[bot]` and `coderabbitai[bot]`; the author then replies to his own bots. 13+ days open, no maintainer comment. Establishes that the maintainer non-response to #30903 was a consistent rejection of the shape, not a one-off bandwidth issue.

**Gates that catch it**:
- `B13-trust-ladder-size` — refuses the size at rung 0/1-3 before commit
- *(future)* `A1-no-audit-dump` — pattern-matches `.audit/`, `.review/`,
  `*-exorcist/`, etc. as new top-level dirs with >50% additions in one
  directory tree. Tracked in `ROADMAP.md`.

**Right shape instead**: host the audit artifacts in *your* repo, link them
from a Design Issue summarizing the top N findings, then file individual
fix PRs that close one finding each. Dicklesworthstone (the bun#30903
author) actually did this — see his #31087, #31092, #31093, etc. — but
filed them alongside the unread audit-PR, which is its own anti-pattern
(see Pattern 4).

## Pattern 2 — The Trust-Ladder Skip

**Definition**: a contributor's first PR to a repo is a multi-area
proposal, umbrella refactor, or "everything we should change" pitch that
requires the maintainer to trust the contributor across many decisions
before they've earned trust across one.

**Why it kills the PR**: maintainer review attention is the single
scarcest resource on a high-velocity project. Reviewing an umbrella from
an unknown contributor costs more than reviewing a small fix from a known
one; the rational response is to wait until the contributor has shipped
a small fix first. So the umbrella sits.

**Real cases**:
- **`oven-sh/bun#30903`** — same case, viewed through the trust-ladder
  lens. Dicklesworthstone had 0 prior merged PRs in `oven-sh/bun`. His
  *first contact* was a 122k-line proposal. Maintainer ratio: dozens of PRs
  merged in the same 11-day window, just not this one.
- **`nodejs/node#61935`** ([link](https://github.com/nodejs/node/pull/61935)) — "Audit of Node.js Technical Improvements and Bug Fixes," opened 2026-02-22 08:01 UTC by poria-lang (0 prior merges in Node.js). Diff was small (9 files, +106/-113), but the *framing* was umbrella ("audit covering webstreams, cluster tests, http2 docs, fs.promises perf"). **Closed 15 minutes later** by @ChALkeR (Node.js TSC) with the one-line review: "Just random hallucinated changes." Demonstrates that the trust-ladder failure is about *framing*, not just file volume.

**Gates that catch it**: `A07-trust-ladder-fit` + `B13-trust-ladder-size`.

**Right shape instead**: find one open issue, fix it in ≤200 LOC, ship it.
Get merged. Repeat 3-4 times. Then pitch your umbrella with the social
proof of recent merges.

## Pattern 3 — The Maintainer-Decision Punt

**Definition**: the PR's body or test plan asks the maintainer to make a
scope decision the contributor should have made before filing. Phrases
like "decide whether to (a) accept this as-is or (b) move the artifacts
to an external location," "let me know if you want me to split this," or
"happy to do whatever you prefer" appear in the PR body.

**Why it kills the PR**: it converts the maintainer's review-time into
*your* product-management time. A maintainer who has 50 other PRs to look
at this week is not going to invent your scope strategy for you. They'll
either close it or never click into it.

**Real cases**:
- **`oven-sh/bun#30903`** — test plan literally includes: "Decide whether to (a) accept this PR as-is (audit artifacts in-tree, fixes follow in separate PRs) or (b) move the artifacts to an external location (e.g., a separate audit repo) and reduce this PR to the executive guide + the META scripts." That's not a test plan, that's a question for the maintainer.

**Gates that catch it**:
- *(future)* `C2-no-maintainer-decision-punts` — phrase-detector pass over the PR body. Tracked in `ROADMAP.md`.

**Right shape instead**: decide first, file second. If the decision is
genuinely the maintainer's call (e.g., "should this feature live in core
or as a plugin?"), file as a Design Issue, *not* a PR.

## Pattern 4 — The Review Queue Pile

**Definition**: contributor opens 2+ unreviewed PRs on the same repo in
quick succession, often building one on top of the other or claiming
they're "independent" when they share context the maintainer hasn't yet
seen.

**Why it kills the PR**: each new PR raises the cost of looking at any of
them. The maintainer can't review #2 without context that's still
unmerged in #1. The pile produces a review deadlock — the maintainer
postpones reviewing any of them until the umbrella context (or the first
PR) is dealt with.

**Real cases**:
- **`oven-sh/bun` Dicklesworthstone batch (#31087, #31092, #31093, #31107, #31108, #31140, #31204, #31248, #31258, #31267)** — 10 surgical fix PRs filed across 4 days (May 19-23, 2026) while the umbrella audit-PR #30903 sat unread. Each individual PR is genuinely well-shaped: closes a specific `EXP-NNN` finding, has a Miri witness, includes an in-repo test. But the maintainer can't review any of them without the audit context that's stuck behind their #30903 vote. All 10 still open as of 2026-05-28.

**Gates that catch it**:
- *(future)* `D6-review-queue-throttle` — refuses to open a 3rd PR when 2 prior PRs on the same repo are unreviewed. Tracked in `ROADMAP.md`.

**Right shape instead**: ship one. Wait. If reviewed: ship the next. If
silent after >7 days: comment politely on the silent PR offering to split
or pause; *do not* open another PR.

## Pattern 5 — The Generated-Artifact Bloat

**Definition**: the diff is dominated by generated material with no
human-engineered code at its center: per-finding JSON registries, raw
ast-grep output, every round's convergence file, vendored Cargo build
trees, transpiler output, etc.

**Why it kills the PR**: a maintainer cannot review what they cannot
read. A 50KB JSON registry of findings doesn't compile, doesn't pass
tests, doesn't fit in the project's mental model. Generated content
belongs in your repo or a gist; only the *summary* belongs in the
maintainer's tree.

**Real cases**:
- **`oven-sh/bun#30903`** — includes `phase1_*` through `phase11_*` JSON files, every round's convergence JSON, per-EXP Miri/loom logs, raw ast-grep output, per-experiment Cargo build trees (excluded via `.gitignore` only because the author explicitly noted them).
- **`oven-sh/bun#30763`** — 44 commits, most of which are the author tidying his own audit dir ("drop empty scratch files," "restore .log files," "re-drop raw dumps").

**Gates that catch it**:
- `B13-trust-ladder-size` catches it on size + new-top-level-dir grounds.
- *(future)* `A1-no-audit-dump` would name it explicitly.

**Right shape instead**: include the executive summary in the PR (or as
a Design Issue). Link out to the artifact corpus hosted in your repo.

## Pattern 6 — The Multi-Agent Authorship Brag

**Definition**: the PR body or commit footers prominently advertise that
multiple AI agents contributed (Claude + Codex + Gemini + ChatGPT + ...).
The framing positions multi-agent generation as a credential.

**Why it kills the PR**: for a maintainer who has already been targeted
by AI slop, "Claude, Codex, and Gemini all contributed" is a red flag, not a
credential. The maintainer reads it as "this contributor has limited
ability to validate the output of any one agent and is hoping that
ensemble agreement substitutes for first-principles understanding."

**Real cases**:
- **`oven-sh/bun#30903`** — body says "Multi-agent authorship. Claude, Codex, and Gemini all contributed. Per-doc attribution is in the `CODEX_*.md` filenames." Reactions: 3 thumbs-down.
- **`oven-sh/bun#30763`** — Co-Authored-By footer cites `Claude Opus 4.7 (1M context)`. Reviews dominated by `claude[bot]` and `coderabbitai[bot]`; no human maintainer engages.

**Gates that catch it**:
- *(future)* — there isn't a clean gate for this. The dossier's
  `ai_disclosure_required` field captures the repo's *policy*; the
  contributor needs judgment about whether to *additionally* advertise
  multi-agent authorship in the PR body. Currently advisory only.

**Right shape instead**: disclose AI assistance honestly (commit footer
is fine, per-repo policy applies), but don't position the multi-agent
fact as a strength. A maintainer cares about your validation rigor, not
your tool stack.

## Common signatures (for grading a closed PR or pre-flighting yours)

If 3 or more of these appear, the PR almost certainly hit one of the
patterns above. Use as a checklist before clicking "Create pull request":

1. ☐ PR body announces "audit" / "comprehensive" / "exhaustive" /
       "every X" / "all Y"
2. ☐ File count vastly exceeds the lines-changed-per-file ratio
       (generated material, not engineered code)
3. ☐ AI co-author lines on every commit (Claude / Jules / Codex / etc.)
4. ☐ Author has 0 prior merges in the target repo
5. ☐ Bot reviews (CodeRabbit, Claude, Gemini) dominate the review pane;
       human maintainers are absent or one-line dismissive
6. ☐ PR body includes "decide" / "let me know" / "your call" /
       "agent operating route" / "happy to do whatever you prefer"
7. ☐ Self-replies and self-cleanup commits dominate the timeline (the
       author tidying their own work in the review thread)
8. ☐ "Test plan" includes "maintainer reads X document"

## When to add a new pattern

A new entry lands when:
- You've personally observed the same failure mode at **two or more
  distinct repos** (not just one bad PR — that's a case study, not a
  pattern); OR
- The pattern has a clean, gate-able definition that fits the existing
  `gates/<phase><N>-<slug>.sh` slot system; OR
- A maintainer of any tracked repo (per `~/.contribute-system/research/*`)
  has called out the pattern by name in a review comment or
  CONTRIBUTING.md.

When adding a new pattern, also propose the gate that would catch it
(even if you don't ship the gate immediately) and append it to
`~/.contribute-system/ROADMAP.md`.
